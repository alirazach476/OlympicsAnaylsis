1. Project summary — the 60-second pitch

Olympics Analysis is a full-stack data platform covering every Summer Olympics from Rome 1960 to Paris 2024 and every Winter Olympics from Squaw Valley 1960 to Milano Cortina 2026.

I built the whole chain: data collection from Olympedia and Wikipedia, a layered SQLite data warehouse (bronze → silver → gold, 116 tables, 2.7 GB), a FastAPI backend with 100+ endpoints, and a React + TypeScript website that presents results like a TV broadcast.

Every Games has its own visual identity: the site recolours itself from each edition's logo and artwork. Users can drill down from an edition to a sport, an event, and every round, heat, match and bout — or explore any country's complete Olympic record, medal statistics and 100+ analytics charts.

What a user can do

  • Global Overview — Olympic-wide statistics, every edition with its emblem, historical charts.
  • Summer / Winter Olympics — galleries of all editions; upcoming Games (LA 2028 → Salt Lake 2034) marked Coming soon.
  • Edition page — themed hero with mascot; Medal Standings, Event Results (sport pictograms → events), Participants (all 14,884 entries for Tokyo 2020), Sports, Records, Venues, Gender Statistics.
  • Event results — every saved Olympedia table; team squads folded under “+”; match, bout and heat detail pages with previous/next navigation; broadcast scoreboards per sport.
  • Countries & Medal Statistics — the complete table of 231 NOCs with filters; country profile with Visuals and Results (a sidebar of every Games and the country's full Olympedia table).
  • Athletes, Records, Analytics — rankings, record books, statistics, machine-learning backtests, team-sport analysis.

Why it is interesting technically

  • Real, messy, historical data: renamed countries (USSR, East/West Germany, ROC), team events, ties, boycotts, many result formats.
  • A strict honesty rule: nothing is invented. Missing values stay empty; links only exist when the target exists.
  • A data-driven design system: one theme engine restyles 39 editions without per-page CSS.
  • Production concerns: virtualised tables for 15k rows, URL-driven state, browser history, lazy loading, accessibility, 350+ tests.

The website and the API are separate. The browser always calls /api/... on the same domain; Vercel forwards those calls to the API host. This avoids CORS and means the frontend code never changes between local development and production.

Request flow example — opening an event page

  1. User opens /games/2024_summer/events/19000360. React Router renders EventResultsPage.
  2. TanStack Query calls GET /api/events/19000360 (cached for 5 minutes, de-duplicated).
  3. FastAPI loads the saved Olympedia tables for that page, adds in-app routes to every link (athletes, matches, heats), and returns JSON.
  4. The page classifies each table (heat / final / match list / bout) and renders the matching broadcast component, themed for Paris 2024.

4. Data pipeline & warehouse

Sources

  • Olympedia — the reference database of Olympic results: event pages, rounds, heats, match and bout pages, country-by-edition pages, records.
  • Wikipedia (MediaWiki API) — edition information, venues, assets (logos, backgrounds, mascots, pictograms).
  • Open historical datasets for cross-checking athlete participations.

Layers (medallion architecture)

LayerContentsExamples
BronzeRaw collected data, exactly as published, with source URL and timestampolympedia_pages, olympedia_page_tables (211,403 saved tables), wikipedia_pages
SilverCleaned, typed, linked entitiessilver_participations (263,893 rows), silver_medal_awards, olympedia_matches, olympedia_page_links (94,489 links), athlete id cross-reference (124,926)
GoldBusiness-level marts served by the APIgold_country_medals, gold_edition_performance, gold_sport_performance, gold_records

Pipeline properties

  • Resumable — every stage records progress, so a crash or a rate-limit pause resumes where it stopped.
  • Polite — rate limiting, retries with back-off (tenacity), respect for robots rules; no authentication or CAPTCHA bypass.
  • Validated — 37 expectation checks (row counts, referential integrity, medal reconciliation, link resolution).
  • Provenance — every record keeps its source URL; the UI links back to Olympedia.
Medal counting convention. One medal per podium place per NOC per event (a team medal counts once; ties each count). Historical NOCs are never merged: URS, EUN, RUS, ROC, OAR, AIN, GDR, FRG, EUA and GER stay separate rows. Result: USA at Paris 2024 = 40 gold, 44 silver, 42 bronze, matching the official table.

5. Backend API (FastAPI)

The API is organised in routers: platform (games, countries, athletes, records), olympic (Olympedia-style pages), pages (matches, scoreboards), viz (100+ chart datasets), explorer and routes.

EndpointReturns
GET /api/games?include_upcoming=1All 39 editions with headline numbers; upcoming Games flagged.
GET /api/games/{id}/eventsEdition event index grouped by sport (with match / heat counts).
GET /api/events/{id}One event: header facts, podium, stages, every saved table with in-app links, siblings for prev/next.
GET /api/subpages/{id}A match, bout or heat page with its position in the event (n of m).
GET /api/matches/{id}Scoreboard data: teams, periods, statistics, goals, cards, line-ups, officials.
GET /api/medals/countriesMedal table with filters (season, years, edition, sport, gender, medal), ranks, appearances.
GET /api/countries/{noc}/resultsEvery entry of a country across all Games (USA: 10,366), medal or not.
GET /api/countries/{noc}/olympedia/{games}The country's full Olympedia table for one edition, with links.
GET /api/games/{id}/participants · /genderAll athlete entries; gender breakdown by sport, NOC and event.
GET /api/viz/chart/{id}Data + metadata for one of 100+ registered charts.

Design decisions

  • Link annotation — saved Olympedia links are turned into in-app routes only when the target page exists (no dead links).
  • Caching — expensive indexes (edition event index, appearances) use lru_cache; overview data uses a TTL cache.
  • CSV everywhere — list endpoints accept ?format=csv.
  • Honest joins — e.g. participant events are matched to result pages only on exact normalised names (81% of Tokyo 2020 entries link; the rest stay plain text rather than guessing).

6. Frontend (React)

  • Routing — 40+ routes, lazy-loaded pages; canonical redirects (a link with the wrong edition is corrected so the theme always matches the data).
  • URL state — a useParamState hook stores filters in the query string; a small shared store composes several updates in one click (sort + order) into one history entry.
  • Scroll manager — new pages start at the top; Back/Forward restore the exact scroll position after data loads.
  • Keyboard safety — arrow keys on a closed dropdown scroll the page instead of silently changing a filter.
  • Performance — virtualised tables, lazy charts (load when scrolled into view), keep-previous-data, code-split bundles.
  • Accessibility — semantic tables, labelled controls, focus states, reduced-motion support, dark & light themes.

7. Edition theme engine

A build script reads each edition's logo and background, extracts a colour palette with Pillow, and writes a registry (editions.json). At runtime themeVars() converts an edition into CSS variables: primary/secondary/accent colours (adjusted to WCAG contrast), tinted surfaces, the palette stripe, the deepest colour for header bands, and the artwork/emblem URLs. Every component uses those variables — so switching from Rio 2016 to Beijing 2022 restyles the menu, page background, table headers and scoreboards with no per-page CSS.

8. Broadcast tables & scoreboards

  • Tables — dark header band with the edition emblem (left) and sport pictogram (right); rows as cards; gold/silver/bronze rows tinted with a medal bar; qualifiers marked; squads folded under “+”; CSV export.
  • Scoreboards — one shared frame (edition, sport, stage ribbon, venue) and a sport-specific body: football HT/FT/extra time and scorers, basketball line score, volleyball sets, ice hockey periods, curling ends and hammer, baseball R-H-E, boxing corners, athletics/swimming/gymnastics leaderboards.
  • Abbreviation legend — explains only the codes present on the page (DNS, DNF, DQ, Q/q, OR/WR, “Match 1/2” = gold-medal match).

9. Data quality & honesty rules

Never invent data. No fake records, no guessed meanings, no decorative links. If a value is missing it is shown as “—”; if a pictogram is missing the sport's initials are shown instead of a random icon; codes whose meaning the data does not establish are left unexplained.
  • Example: the 2021 men's hockey final shows 1–1 because the shoot-out is not recorded; the board does not make up the result.
  • Example: a baseball header score disagreed with the box score — the R-H-E box is used as the authority.
  • Example: one Tokyo 2020 athlete has no recorded gender — reported as “unrecorded”, never guessed.

11. Deployment — the site runs when your PC is off

  • Website — Vercel builds the React app and serves it from a global CDN: https://olympicsanaylsis.vercel.app. Always on, free.
  • API + database — packaged as a Docker image (deploy/huggingface/). The 2.7 GB warehouse is stored in a private Hugging Face dataset and downloaded by the server on first start.
  • Connection — frontend/vercel.json rewrites /api/* to the API host, so the browser only ever talks to one domain.
  • Code — GitHub repository with the README, screenshots and setup instructions; the database is excluded from git (100 MB file limit) and rebuilt by the pipeline.

13. Interview questions & model answers

Project & motivation

Tell me about this project.
It's an end-to-end Olympic data platform: I collected results from Olympedia and Wikipedia, modelled them in a layered SQLite warehouse, exposed them through a FastAPI backend and built a React website that presents 35 Games like a sports broadcast — every edition themed from its own logo, with drill-down from edition to sport, event, heat, match and bout, plus country, athlete and analytics views.
What was the hardest part?
Data correctness. Olympic history has renamed countries, team events, ties and boycotts. I enforced a rule to never invent data, kept historical NOCs separate, reconciled medal counts with official tables and wrote validation checks. On the frontend, the hardest part was URL-driven state: getting filters, history and scroll restoration to behave like a native app.
What would you improve next?
Move the warehouse to a managed database (for example Postgres or a hosted SQLite service) for multi-user scaling, add incremental pipeline runs for new Games, server-side pagination for the biggest tables, and end-to-end tests in CI on every push.

Data engineering

Why a bronze / silver / gold structure?
Bronze keeps raw data exactly as published, so I can always re-derive; silver holds cleaned, linked entities; gold holds the aggregates the API serves. A parsing bug only requires re-running silver/gold, not re-scraping, and every number can be traced back to its source URL.
How did you scrape responsibly?
Rate limiting, retries with exponential back-off, respecting robots rules, caching pages so nothing is fetched twice, and a resumable design. I never bypassed authentication or CAPTCHAs.
How do you ensure data quality?
37 automated expectation checks (counts, referential integrity, link resolution, medal reconciliation), provenance on every record, and a policy of leaving missing values empty. For example, USA's Paris 2024 medals (40-44-42) match the official table.
Why SQLite instead of Postgres?
The workload is read-heavy analytics by one service, and SQLite gives a single portable file with zero operations and very fast local reads. The project also contains Alembic migrations and a SQLite→Postgres script, so switching is straightforward if concurrent writes or scale require it.

Backend

Why FastAPI?
Type hints drive validation and automatic OpenAPI documentation, it's fast, and it's simple to structure into routers. The /docs page made frontend integration and testing easy.
How did you make the API fast?
Pre-aggregated gold tables, indexes on lookup columns, lru_cache for expensive indexes, TTL caching for the overview, returning only needed columns, and letting the client cache with TanStack Query. A country's 10,366 results return in about 1.6 seconds.
How do you avoid broken links?
The API annotates every saved link with an in-app route only when the target exists (a saved page or a known athlete); otherwise it links to the source or shows plain text.

Frontend

How does the theming work for 39 editions?
A script extracts each edition's palette from its logo into a registry. At runtime a function converts the edition into CSS variables (colours with WCAG-adjusted contrast, tinted surfaces, artwork URLs). Components only use variables, so one theme engine restyles the whole site — no per-edition CSS.
How did you handle very large tables?
Virtualisation with TanStack Virtual: only the visible rows exist in the DOM, so a 14,884-row participants table scrolls smoothly. Sorting and searching run on the loaded data.
Why keep filters in the URL?
Shareable links, refresh-safe state and working Back/Forward. I found a subtle bug: two setters in one click overwrote each other because React Router gives each setter a stale copy of the params. I fixed it with a tiny store that composes updates within the same history entry.
How did you test the UI?
Vitest + Testing Library for components and live-API integration, and Puppeteer suites driving real Chrome through user journeys (click a pictogram, open a match, press Back, check scroll and filters), plus visual sweeps of every edition on desktop and phone.
How do you handle accessibility?
Semantic tables and headings, labelled controls (I renamed duplicate labels like two “Season” filters), keyboard-operable sorting, visible focus, reduced-motion support and contrast-checked theme colours.

Deployment & DevOps

How is it deployed?
The React build is on Vercel's CDN. The API is a Docker image; the 2.7 GB warehouse lives in a private Hugging Face dataset and is downloaded on server start. Vercel rewrites /api/* to the API host, so there's no CORS and the frontend code is identical in development and production.
Why not put everything on Vercel?
Vercel serverless functions have a bundle limit of about 250 MB, and the database is 2.7 GB. Separating a static frontend from a stateful API host is the standard pattern for this case.
How did you keep secrets safe?
The .env file and tokens are git-ignored and excluded from Vercel uploads; before publishing I scanned all 1,487 files for tokens, keys and emails, and replaced a local default password with a placeholder.

Behavioural

Describe a bug you're proud of finding.
Sorting the medal table by a column set the order but lost the column. The cause was React Router's functional updater receiving stale params when two setters ran in one handler. I reproduced it in a browser test, fixed it at the root in the shared URL-state hook, and the same fix repaired “Clear all” buttons elsewhere.
How did you handle changing requirements?
Requirements evolved over many review rounds (layout of edition pages, where pictogram clicks lead, table design). I kept changes behind reusable components and URL state, wrote acceptance tests for each workflow, and re-ran all suites after every change so earlier features never regressed.
